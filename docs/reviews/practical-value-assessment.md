# 現有功能的實際用途測評

後續已完成較完整的 14 個情境測評，請以 [測評結果與證據](../evaluations/RESULTS.md) 為最新結論。下文保留最初 8 個例子的觀察。

實測日期：2026-09-26。這是本地使用測評，不是公開 README，也不是單元測試報告。Git 展示日期與實測日期分開記錄。

## 結論

目前可作為「有固定措辭的專案規則提醒器」，但尚未證明整體工作效率提高。frame 能減少重複輸入指令並保留來源；漏選與誤選則會增加人工檢查。query 能找回現有知識卡，但一張卡的範例不足以證明比人手開檔或文字搜尋更快。

不應把測試通過、輸出更短、執行更快，當成人完成任務更快的證據。沒有執行 coding agent，也沒有量度模型 tokens 或下游改碼品質。

## 比較基準

人手流程：讀任務 → 找相關規則／ADR → 複製需要的內容與來源 → 檢查 prompt → 交給 agent。

現有工具流程：讀任務 → 執行 frame → 檢查有沒有漏選／誤選 → 如需 ADR 另外執行 query → 手動選取並合併 → 交給 agent。

工具主要代替「查找與複製規則」，沒有代替理解任務、確認適用性或整合搜尋結果。熟悉小專案的人可能比呼叫工具更快；規則很多或跨專案工作時才可能顯出價值，尚待量測。

## 實際試跑

使用已打包 JAR，目標 examples/payments（兩條規則、一張知識卡），無模型或網路。以下是人工挑選的小案例，不能當成一般準確率統計。

| 輸入／功能 | 期望的實際用途 | 實際結果 | 對效率的影響 |
|---|---|---|---|
| frame：修改付款重試，避免重複扣款 | 補上付款約束 | 附冪等性、測試要求與來源 | 少一次查找／複製，但仍需確認 |
| frame：支付失敗後再試一次，避免重複扣款 | 同一用途也帶付款約束 | 原文返回，漏選 | 要知道缺了甚麼才能補回；不熟悉專案的人容易漏掉 |
| frame：整理圖片 | 不加付款內容 | 原文返回 | 沒新增干擾，也沒新增價值；多一次呼叫 |
| frame：這次不改付款重試，只整理圖片 | 不加付款內容 | 誤加付款約束 | 要刪掉內容，降低效率 |
| frame：更新 README 的安裝步驟 | 提醒驗證使用步驟 | 附文件規則 | 可提醒，但規則較通用，新增資訊有限 |
| query：付款重試 | 找到付款 ADR | 找到來源與摘錄 | 可直接定位；小資料集未必比開檔快 |
| query：支付失敗後再試一次 | 找到同一 ADR | 找到 ADR | 本例有重疊字詞；不代表理解同義詞 |
| query：README 安裝步驟 | 找文件知識 | 沒有相關本地資料 | 來源沒有這類卡；不能代替尚未建立的知識 |

8 次 JAR 呼叫的單次耗時為 169–305 ms；同一付款任務的 PowerShell wrapper 為 1256 ms。這是一次本機觀察，包含啟動成本；不是穩定 benchmark，更不是人手節省時間。wrapper 每次編譯，頻繁使用應先打包。所有呼叫 exit code 0，仍有漏選／誤選，顯示功能正確執行與用途正確是兩回事。

## 每個功能是否值得保留

| 功能 | 現階段判斷 | 使用條件／限制 |
|---|---|---|
| Frame | 有條件保留 | 固定用語、可人工預覽；不能當成自動完整約束 |
| Query | 保留作輔助查找 | 要有足夠且有用的卡片；尚無優於文字搜尋的證據 |
| Validate | 保留作維護入口 | 格式檢查減少延後發現錯檔；不驗證規則意義 |
| Conflict | 保留 | 能阻止已宣告的已選規則衝突；未宣告或漏選的矛盾無法發現 |
| JAR | 保留 | 減少每次重新編譯，適合重複使用 |
| Skill 入口 | 暫無效率結論 | 只是入口，未測實際觸發、閱讀成本及 agent 成果 |

## 優先改善甚麼

1. 在新增 Web 前，先讓人看清楚「選中了甚麼／沒有選中甚麼」，並可以選擇或排除規則。否定與同義詞不適合靠增加幾條硬編碼特例宣稱解決。
2. 用真實專案的規則／ADR 建立用途案例，包含漏選、否定、不相關與資料不存在的情況。輸出限制與錯誤檢查繼續保留。
3. 若主要用途要結合 ADR 與規則，設計明確的人工挑選／合併流程。現在兩個指令分開，整合成本仍在人身上。
4. 只有上述流程證明有用，才把它做成 Web 操作；漂亮介面不能修正規則選擇問題。

以上是優先方向，沒有在本次文件修改中新增功能或偷偷修補 matcher。

## 怎樣真正證明效率提高

下一次人手比較選 6 個真實任務，預先由人確認適用規則與必要資料；至少包含跨專案、否定、同義表達與無關任務。每種方式使用相同來源，完成可交付 prompt 才停止計時。

- A：人手開檔／搜尋／整理。
- B：PromptForge，再補齊與修正。
- 交替先做 A 或 B，降低第二次熟悉任務的偏差；仍須記錄學習效應。
- 記錄總時間、查找時間、修正時間、缺漏要求、無關內容、能否直接使用，以及首次建卡／維護成本。
- 若要比較 agent 成果，另外使用相同模型、設定與驗收條件；那是獨立評估，不是現有工具的必要依賴。

| 任務 | A 總時間 | B 總時間 | B 修正時間 | A／B 缺漏與無關內容 | 可直接使用？ |
|---|---|---|---|---|---|
| 待使用者實測 | 未量度 | 未量度 | 未量度 | 未量度 | 未確認 |

成功條件：在不增加缺漏／無關內容的前提下，重複任務的總準備時間下降，且累積節省足以抵銷建立與維護規則的時間。若 B 較慢或漏掉關鍵約束，就要改流程或縮小用途，而不是加分數包裝成成功。
