# 現有功能：用途測評結果

實測：2026-09-26，本地 Windows，現有 Java CLI。先固定任務與預期，再執行；沒有為這批案例修改產品程式。資料是合成的電商工作情境，不冒充真實使用者实验。

## 判斷

**有實際用途，但目前只適合人工確認的規則提醒與知識查找；不適合自動決定完整 prompt。尚不能判定人的總效率提高。**

可保留的價值是：固定用語下省去部分查找與複製、提供來源、阻止已宣告的衝突、規則更新不用重新建置。主要代價是：漏選、誤選、搜尋噪音，以及 query 與 frame 分開後仍須人工合併。

## 怎樣測

[協議](PROTOCOL.md) 與 [預先固定的案例](cases.json) 先提交。8 條規則、6 張知識卡、14 個任務，包含同義表達、中英用語、否定、文件修改、無關任務和部署。每個任務都有人工定義的必要規則／知識來源。

透過 `scripts/evaluate-usefulness.ps1` 呼叫 JAR，保存 stdout、stderr、exit code、時間及來源 hash。重跑三輪，frame 的規則選擇與 query 的來源結果一致；下方證據是最後一輪。三輪結果一致只證明穩定，不能消除這個小測試集的偏差。

## Frame：減少複製，但增加補刪

| 測量 | 結果 | 實際意思 |
|---|---|---|
| 完全符合預期 | 8 / 14 任務 | 6 個任務的規則需補回或刪除 |
| 必要規則 | 19 項 | 人手基準應從同一批檔案選出的內容 |
| 正確選中 | 13 項 | 這部分候選內容不用人再逐條複製 |
| 漏選 | 6 項 | 人要先知道缺甚麼，再查找並補回 |
| 誤選 | 3 項 | 人要辨識不適用的約束，再刪掉 |

這不是「省下 13 減 9 個步驟」的時間計算：辨識一個漏選要求可能比複製多條指令更難；檢查每個輸出也有成本。

| 案例 | 觀察到的問題 |
|---|---|
| F02 支付失敗後再試一次 | 未命中付款／重試及修改字詞，漏兩條 |
| F03 不改付款重試，只整理圖片 | 誤加付款規則 |
| F05 修正 log 記錄 | 未命中日誌及修改，漏兩條 |
| F07 修改 migration | 只選測試規則，漏資料庫遷移規則 |
| F09 只改 API 文件標點 | 誤加 API 行為相容性與程式回歸測試 |
| F14 上線新版 | 未命中部署，漏回滾與健康檢查要求 |

否定與文件範圍尤其重要：使用者可能只想處理一個小工作，工具卻把範圍扩大。增加 keyword 可以改善一些漏選，但不能因此聲稱已解決任務理解。

## Query：查找有幫助，仍需要篩选

需要知識卡的 9 個任務，必要卡片全都排第一，沒有漏掉指定來源。共返回 23 個項目，其中 14 個不在預先指定的必要來源內。

讀後可確認：日誌任務返回 API 相容性，README 安裝任務返回 migration，欄位相關任務又返回 privacy，這些增加篩選負擔。API 文件任務返回相容性卡可能提供背景，不能把每個未指定項目一律算成錯誤。F03 否定付款任務仍返回付款卡，並不理解「這次不改」。

本組資料很小，卡片內容也特意覆蓋任務相關詞。9/9 不能推廣成真實專案的搜尋準確率。可以確認「能定位相關來源」；不能確認「比開檔或普通文字搜尋快」。另外，搜尋來源正確不代表摘錄已足以滿足完整任務；目前還要手動合併到 prompt。

## 維護與錯誤攔截

| 操作 | 實際結果 | 用途 |
|---|---|---|
| 缺 instruction 的規則執行 validate | exit 3，指出檔案及缺欄位 | 及早發現壞設定 |
| 修改 rule 後直接重跑同一 JAR | 從版本一變成版本二，沒有重打包 | 可更新自己的規則 |
| 互相衝突的規則被同時選中 | exit 6，stdout 空，stderr 有雙方來源 | 避免輸出已宣告的矛盾指令 |
| 衝突專案執行 validate | exit 0，兩條格式合法規則 | validate 不能當成「規則已適用／無矛盾」批准 |

沒有測得維護花多少人力；建立關鍵字、宣告衝突與維持知識卡都是持續成本。

## 效率結論與優先順序

最後一輪 frame 呼叫為 153–169 ms，query 為 172–248 ms，包含 JVM 啟動。這只說明本機呼叫成本，不是人完成工作的時間；測評未呼叫 coding agent，沒有 token 節省或改碼成果證據。

1. **先保留規則來源、格式驗證、衝突攔截及直接更新資料。** 這些作用清楚，但仍需要人 review。
2. **優先加入可見的規則選擇／排除與缺漏檢查流程。** 先解決需要人補刪的負擔，不用同義詞與否定硬編碼把本測試集刷成全對。
3. **讓知識查找能由人挑選後加入候選 prompt。** 列明選了甚麼及來源，減少另開 query、复制、合併的工作。
4. **再做 Web 操作。** 介面若能實際減少上述操作才有意義；畫面漂亮或有 Spring Boot 不等於效率提高。

對固定措辭且反覆使用同一批規則的人：值得試用。對不熟悉專案、自然表達且希望工具自動補完整要求的人：目前不足以放心依賴。總效率是否提高，要再以真人同資料任務對照總準備時間、修正時間與缺漏；現階段不報假造節省百分比。

## 證據與重跑

- [完整結果 JSON](results/2026-09-26.json)：每個任務的預期、實際輸出、補刪項目、時間及 source／fixture hashes。
- [案例資料](cases.json) 與 fixtures/shop：可以直接查看預期與來源。

在專案根目錄執行：

```powershell
.\scripts\evaluate-usefulness.ps1
```

先打包再執行；產物在 build/usefulness-evaluation。只有需要的成功案例、錯誤攔截符合契約時 runner 才完成，但 exit 0 不代表用途評估全對；必須讀 summary 和各案例結果。規則與 query 品質沒有達標不能用「runner 成功」掩蓋。
